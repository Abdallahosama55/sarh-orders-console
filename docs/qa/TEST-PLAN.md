# Test plan — Orders Console

Covers every requirement in [`../specs/01-requirements.md`](../specs/01-requirements.md). Results are in [`QA-REPORT.md`](QA-REPORT.md).

## 1. Risk-based focus

Effort goes where a defect would hurt most, in this order:

| Risk                                                                   | Why it matters                                   | How it is attacked                                                                                                                                                          |
| ---------------------------------------------------------------------- | ------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Duplicate order** from retries, double submits or concurrency (R2-4) | The client's biggest complaint, and money        | Parallel requests in-process (2 and 20), two OS processes sharing one database, schema-level constraint tests, a lost-response fault in a real browser, a reload mid-submit |
| **Stale results** after rapid filter changes (R1-8)                    | Graded by hand; wrong data looks right           | Out-of-order responses (component + browser), a response that is never cancelled, abort assertions, mutation of the safeguards                                              |
| **Auth bypass / privilege escalation** (SEC-1…8)                       | Every inherited flaw is a real attack            | One test per finding: forged, `alg:none`, expired, revoked and query-string tokens, operator injection, agent delete, CSRF origin                                           |
| **Slow or wrong list queries at 50k rows** (R1-4, R1-5, R1-7)          | "Instant" is a requirement                       | Exhaustive paging against an independent SQL oracle (ties included), `EXPLAIN QUERY PLAN` assertions, benchmark at 50k                                                      |
| **Slow stats blocking or leaking work** (O1)                           | The UI must never block; work must stop on leave | Abort on unmount (component + browser), server-side skip on disconnect, error + single retry                                                                                |

## 3. Techniques

- **Oracle testing.** Paging results are compared row by row with a plain `ORDER BY …, id` query over the same data: every sort × direction × status combination, and searches whose matches share a timestamp.
- **Boundary values.** Riyadh midnight (`20:59:59.999Z` vs `21:00:00.000Z`), DST days in New York, `limit` 100/101, quantity 0/1, prices `0`, `0.01` and `12.345`, the count cap at 10,000 / 10,001, search lengths 2 and 3 (LIKE vs trigram).
- **Fault injection.** Requests held back to reorder responses, a response dropped after the server committed (`route.fetch()` then `abort`), 503s, connection resets, a page reload with a request in flight, clients that never honour `AbortSignal`.
- **Concurrency.** 2 and 20 identical requests in parallel, split across two OS processes.
- **Mutation checks.** Each safeguard is removed in turn (signature check, revocation, server-side role check, fingerprint compare, keyset strictness, tie-breaker, origin check, rate limit, input validation, stats abort, LIKE escaping, abort signal, `keepPreviousData`, key reuse, draft persistence, the double-submit guard, router `flushSync`…) and the suite must fail.
- **Exploratory browser QA.** Scripted Playwright walkthroughs of the dev server and the production build (`vite preview`), with screenshots and console capture.

## 4. Environments and data

macOS 26.5 on an Apple M4, Node 22.17.1, npm 10.9.2 (installs also checked with npm 11.21.1 and 12.2.1), SQLite 3.53.2 via better-sqlite3 12.11.1, Chromium from Playwright 1.63.0. Each API test suite seeds its own temporary database file (WAL, triggers and FTS included). The E2E stack seeds `data/e2e.db` (50,000 orders) on ports 3101/5174. The dev database is never touched by tests.

## 5. Entry and exit criteria

- **Entry:** the spec IDs exist, `npm install` succeeds, `npm run setup` seeds 50,000 orders.
- **Exit:** `npm run verify` passes (types, lint, format, all Vitest tests); `npm run test:e2e` passes, 3× repeated with no flakes; `npm run proof:duplicates` prints PASS; the bench worst p95 is under 50 ms; every P0 requirement below has at least one automated test that fails when its safeguard is removed; `npm audit` reports 0 vulnerabilities; a fresh clone installs, seeds and tests in under five minutes.

## 7. Manual script for reviewers (10 minutes)

1. `npm run setup && npm run dev`, sign in as the agent. Expect "10,000+ orders", newest first.
2. **R1-8:** tick DEV → _Slow list requests_, then click Paid, Shipped, Cancelled within a second. Expect only Cancelled rows, and earlier requests _(canceled)_ in DevTools → Network.
3. Scroll fast for a few seconds. Expect rows to keep appearing, with about 40 `role=row` elements in the DOM.
4. Search `harbi`, then `العتيبي`, then `#4242`. Reload. Expect the same view.
5. **R2:** New order → fill in → double-click Create order. Expect one "Order #… created" and one row in the list. Run `npm run proof:duplicates` and expect PASS.
6. **O1:** Overview → leave within 3 s. Expect _(canceled)_ and `stats report skipped` in the API log. Tick _Make stats requests fail_ → error → untick → Retry.
7. **SEC:** sign in as the agent → open an order: no Delete. As admin: Delete → confirm → the order disappears.
